# 项目功能、计费与上游更新评估

评估日期：2026-10-15。评估基线：`v1.3.22`（Panel 1.3.22，Node 1.3.10）。

> 以下是修复前评估证据，不代表修复后状态；候选版 1.4.0 的交付规则与发布边界见 [发布运行手册](../RELEASE-1.4.0.md)。

## 一、结论

**转发管理功能较完整，但当前计费链路不宜直接当作可靠的收费系统。用户感觉“奇怪”有实际原因，不只是操作习惯。**

主要问题集中在三层：

1. **计量不可靠**：长 TCP 连接在结束前不入账；上报已入账但响应丢失时，重试会重复入账。
2. **套餐规则混用**：月付提前续费延长有效期，却立即重置额度；非月付的“额度叠加 + 已用清零”又会额外返还历史消耗。
3. **扣款和权益状态不一致**：旧管理员表单可以覆盖新余额；降级不限制已有规则；注册可显示套餐却没有该套餐的线路授权；封禁后仍会自动扣款。

建议：**保留本分支的多跳等能力，定向移植上游可靠性修复，先统一计费规则，再考虑增加在线支付。不要直接替换上游镜像或合并整个上游 main。**

本轮仅新增本报告；未修改业务源码、现有数据库、Git 分支或部署配置，未执行上游合并或发布。

后续实施状态见[计费可靠性第一批实施记录](billing-hardening-2026-10-15.md)与[第二批及发布候选验收记录](release-validation-2026-10-15.md)。上段描述的是评估完成时的状态，不代表后续代码没有变化。

## 二、范围与验证边界

- 梳理前端路由、后端 API、SQLite/PostgreSQL 仓储、节点转发与上报、调度任务、部署与发布流程。
- 运行已有测试，并用当前编译产物启动独立临时 Panel/Node，复现购买、续费、扣量、注册、充值和管理员编辑场景。
- 所有复现场景仅写入新建临时数据库；未使用项目根目录的 `data.db`。
- 对照上游源码、提交历史、Release、开放 Issue/PR，而非只比较版本号。
- 未连接生产环境，不能据此断言实际用户已经被多扣多少；未逐页做人工浏览器验收。
- 本机为 macOS；Linux splice/TFO 的实际数据路径及 PostgreSQL 实例仍需在 Linux/PG 环境复验。

### 当前“付费”的真实链路

```text
管理员发兑换码 / 人工设置余额
           ↓
用户账户余额
           ↓
购买套餐 / 到期自动续费
           ↓
扣余额 + 更新额度、到期时间、授权 + 生成购买订单
           ↓
节点流量上报 → 实际字节 × 线路倍率 → 消耗流量额度
```

流量消耗扣的是套餐字节额度，**不是按流量实时扣钱**。购买订单也不是支付平台的收款凭证。若运营目标是自动收款销售，目前缺少一个完整支付层。

## 四、计费与权益问题清单

优先级：P0 = 正式收费前的阻断项；P1 = 尽快修复；P2 = 规则明确后改进。业务争议项不等同于所有配置下都算程序错误。

### B01 · P0 · 流量重试会重复扣量【实测】

- 同一批 `{upload:100, download:200}` 上报两次，用户计费流量从 **300 变为 600 字节**。
- 节点只在收到成功响应后清理计数；如果面板已经提交但响应丢失，下一次会重新发送包含旧字节的快照。
- 协议没有批次 ID，数据库也没有已处理批次记录。事务只能保证一次请求内部原子，不能判断两次请求是不是同一份流量。
- 位置：`crates/node/src/reporter.rs:405`、`crates/shared/src/protocol.rs:718`、`crates/panel/src/db/sqlite_repo/traffic.rs:30`；PG 同样没有批次去重。
- 修复：优先移植上游 #142；节点保留固定批次 ID 和固定内容，面板将去重记录与扣量放在同一事务。Panel 与 Node 必须一起提供这项能力。

### B02 · P0 · TCP 长连接结束前不计量，额度不能及时生效【实测】

- 临时用户额度 **1,048,576 字节**，真实 TCP 回显传输 **1,433,600 字节**。
- 连接保持打开、等待多次上报后，账户已用仍为 **0**；连接关闭后才变为 **1,433,600**。
- 这会形成“使用时不涨、断开后突然暴涨”，长期连接可在面板尚未发现超额时继续转发。
- 普通 TCP 在复制循环结束后汇总；Linux splice 路径在双向复制返回后汇总。WS/TLS 也有结束时汇总路径。
- 位置：`crates/node/src/forwarder/tcp.rs:365-447`、`crates/node/src/forwarder/ws.rs:269-311`、`crates/node/src/forwarder/tls.rs:226`。
- 修复：参考上游 #123，按已成功转发的块增量计数；同时覆盖 splice、限速、WS/TLS、自定义链与预设隧道入口。必须维持中继/出口不重复收费。
- 即使修复，也只是把误差降至上报/配置轮询窗口，不应承诺字节级即时硬限额。

### B03 · P1 · 管理员旧表单能覆盖已经扣掉的余额【实测】

- 管理员打开余额 **80** 的用户编辑窗口；期间用户购买后余额变为 **70**。
- 管理员按现有前端保存形状提交旧表单，即使没有主动修改余额，余额也被写回 **80**。
- 前端只要余额字段非空就提交，后端直接设置绝对余额；没有校验打开表单时的余额/用户版本。
- 位置：`frontend/src/pages/Users.tsx:249-276`、`crates/panel/src/db/sqlite_repo/user_groups.rs:131`；PG 同类更新也需处理。
- 修复：未变字段不发送；显式余额调整用独立接口、变动金额、原因和幂等键；后端用版本/CAS 校验并写入财务账本。仅修前端不足以解决显式调余额的并发。

### B04 · P1 · 月付提前手动续费把“买下一周期”和“立即重置”混在一起【实测】

| 项目 | 续费前 | 提前购买同套餐后 |
|---|---|---|
| 到期时间 | 2026-11-14 | 2026-12-14 |
| 总额度 | 1,000,000 | 1,000,000 |
| 已用 | 800,000 | 0 |
| 余额 | 90 | 80 |

- 有效期延长 30 天，但立刻丢弃原周期已用状态，未来那一个月也没有单独的额度重置点。
- 自动续费只在最终到期时运行：若用户把延长后的额度用完，可能要等整个延长有效期结束才有下次周期重置。
- 位置：`crates/panel/src/db/sqlite_repo/settings.rs:825-938`，PG 对应 `settings.rs:925-1043`。
- 建议采用一种明确模型：
  - **提前续费**：购买未来周期，当前额度不动，到周期边界再重置；或
  - **立即重购/重置**：当场开新 30 天周期，明确旧剩余失效，不再叠加剩余时长。
- 不要继续用同一个“购买”按钮隐式混合这两种动作。

### B05 · P1 · 自动续费确认没有绑定具体套餐【实测】

- 用户从月付套餐 A 切换到同价、同 `billing_revision` 的套餐 B 后，A 页面上的旧确认请求仍成功为 B 开启自动续费。
- `billing_revision` 是每个套餐自己的数字，不是全局唯一合同标识；不同套餐可能都是版本 1。
- 位置：`crates/shared/src/protocol.rs:1458`、`crates/panel/src/db/sqlite_repo/users.rs:457-498`；PG 同类检查需同步。
- 修复：确认请求和原子校验加入 `expected_plan_id`，最好绑定订阅/权益版本，而不只是价格和套餐内部版本号。

### B06 · P1 · 封禁用户仍会自动续费扣款【实测】

- 已开启自动续费、过期且余额 90 的用户，封禁后下一调度周期仍扣至 **80**；暂停用户也一样。
- 候选查询和扣费事务均未排除 `banned` / `suspended`。
- 位置：`crates/panel/src/db/sqlite_repo/settings.rs:415-460`、`crates/panel/src/service/monthly_renewal.rs:29`，PG 同样需复核。
- 封禁用户无法登录取消续费，建议封禁时撤销授权，调度与事务再重复检查。
- 暂停是否继续收月租属于产品政策，需明确告知；不要把“暂停转发”和“暂停扣费”混成一个未说明的状态。

### B07 · P1 · 套餐降级不限制已经存在的规则【实测】

- 用户已有 3 条运行规则，从规则数上限 10 的套餐切换到上限 1：**3 条都未暂停，节点配置仍下发 3 条**。
- `max_rules` 主要用于创建限制，没有在购买降级后收敛存量运行规则。
- 位置：`crates/panel/src/db/sqlite_repo/settings.rs:648-1088`、`crates/panel/src/db/sqlite_repo/rules.rs:1878-1894`。
- 上游 #118 已处理购买后的存量规则限制和恢复限制，值得移植。
- 先明确限制的是“保存规则数”还是“运行规则数”；保留规则但暂停超额项更利于用户恢复，不建议直接删除。

### B08 · P1 · 同 ID 套餐改成不限流量后，续购仍然有限额【实测】

- 套餐目录 `traffic=0` 表示不限；现有用户购买同一套餐后，用户限额仍是旧的 **3,000,000**。
- 原因是非月付续费直接算 `current_traffic_limit + traffic_to_add`，把“不限”当作普通数字 0。
- 位置：`crates/panel/src/db/sqlite_repo/settings.rs:827-840`；PG 同逻辑。
- 修复：对“不限”单独分支；同时明确从不限改有限套餐时如何迁移，不能用普通加法处理哨兵值。

### B09 · P1 · 兑换码过期时间只验证能解析，没有规范化存储【实测】

- 生成过期时间 `2026-9-1 00:00:00` 的兑换码，**2026-10-15 仍可成功充值**。
- chrono 接受非补零时间，但 SQL 按文本比较：`2026-10...` 排在 `2026-9...` 前面。
- 位置：`crates/panel/src/api/redeem.rs:79-101`、`crates/panel/src/db/sqlite_repo/redeem.rs:69-76`。
- 公告 `parse_expiry` 也返回输入原文，有相同缺陷；管理员套餐改期已做严格规范格式比较，不必重复替换。
- 修复：统一 UTC 时间解析并补零格式化后存储；对已有非规范时间做审慎修复。参考上游 #138。

### B10 · P1 · SQLite 充值并发时大量返回数据库错误【实测】

- 同一临时用户同时兑换 20 个不同有效码：**5 次成功，15 次业务 code=500**。
- 充值事务仍使用先读后写的 `DEFERRED`；并发写入后读快照不能安全升级写锁。
- 位置：`crates/panel/src/db/sqlite_repo/redeem.rs:46-59`。
- 这是请求失败，不等于已证明重复充值或丢余额；失败后码应仍可重试，需纳入回归。
- 修复：参考上游 #138 使用 `BEGIN IMMEDIATE`，并检查同码并发、异码同用户并发、余额上限、失败回滚。PG 已有行锁，不要机械套 SQLite 修法。

### B11 · P2 · 非月付“额度叠加 + 清零已用”会返还历史消耗【实测，业务规则争议】

- 原额度 1,000,000、已用 800,000，再买同套餐且 `reset_traffic=true`：额度变成 **2,000,000**、已用 **0**。
- 若期望“剩余 200,000 + 新买 1,000,000”，实际多出 800,000。连续续购会不断恢复过去已经消费的额度。
- 位置：`crates/panel/src/db/sqlite_repo/settings.rs:834`、`:896-913`。
- 当前代码和选项确实允许这种行为，不能一概称为违背现有配置；但作为商品模型非常容易误配。
- 建议普通流量包只叠加剩余权益，重置型商品只替换周期额度；历史流量单独保存，不复用一个开关决定财务效果。

### B12 · P2 · 注册显示已分配套餐，但未应用线路授权【实测】

- 允许注册选择包含线路的月付套餐后，新用户账户显示该套餐、额度和到期时间，但 `available_groups=[]`、`all_groups=false`。
- 注册只复制用户额度字段，没有复制 `plan_device_groups` / `grant_all_groups`；管理员默认套餐开户也有同类路径。
- 位置：`crates/panel/src/db/sqlite_repo/users.rs:176-195`、`:198`。
- 若注册即送试用，应明确调用统一的试用权益开通；若必须付费才开通，注册选择应是“意向套餐”，不要伪装成当前已生效订阅。
- 直接把付费套餐设为注册默认还会与 B04 交叉：首次真正付款可能按“同套餐续费”延长已经预分配的期限。

### B13 · P1 · 自助购买缺少服务端幂等与当前套餐前置条件【部分实测】

- 连续重复提交同一购买内容，余额 90 → **70**，新增两笔订单；前端按钮锁不能覆盖响应丢失后重试、多个标签页或 API 客户端。
- 两次明确购买本来应该扣两次；缺陷在于系统没有“同一次交易重试”与“新的购买意图”的标识。
- 管理员代购已有 `expected_current_plan_id`，自助购买却传 `None`；另一标签页切换套餐后，旧确认可能按新的当前状态执行覆盖性切换。后一场景为代码确认，未单独做浏览器复现。
- 位置：`crates/shared/src/protocol.rs:1419-1453`、`crates/panel/src/api/admin/shop.rs:186-201`。
- 修复：交易意图 ID/幂等键 + 用户当前订阅版本 + 服务器报价/结果预览；与扣款、订单、权益同事务持久化。

## 五、非计费问题与体验问题

### 已确认的技术缺口

| 问题 | 证据 | 优先级 |
|---|---|---|
| 弱 JWT 密钥可启动 | 临时实例使用三字符测试密钥正常启动；`crates/panel/src/config.rs:128` 只拒绝空值与示例值 | P1；配置较弱时风险高，参考 #137 |

### 需要整理的业务交互

- 商城月付分支优先显示月付提示，**切换到不同月付套餐时没有同时显示原剩余权益作废的专门警告**：`frontend/src/pages/Shop.tsx:272-283`。
- 套餐编辑目前不会追溯更新已有用户授权，这是代码明确的购买时快照策略，不是自动漏同步。应展示“仅影响未来购买/续费”；目前套餐名称、类型又直接来自可变目录，容易与已开通权益混淆。
- 修改套餐名称、隐藏状态或提交相同值也可能关闭自动续费：`sqlite_repo/settings.rs:168-177` 根据字段是否出现判断账单变化。安全上保守，但运营者与用户缺少明确提示/通知。
- 账户页缺少统一的“正常 / 流量耗尽 / 已到期 / 待续费 / 续费需重新确认”状态及下一次重置时间；只显示余额、日期和用量，不足以解释不能转发的原因。
- 价格没有明确币种；规则数 0 实际表示不限，但有些界面直接显示 0；流量输入写 GB 而计算使用 1024³，建议统一显示 GiB 或明确口径。
- 到期时间使用 UTC 字符串，部分界面直接原样展示，管理员日期选择器也按字符串写回；至少统一标注 UTC，避免把本地时间当成 UTC。
- 当前只有订单与兑换记录，没有统一余额变动账本；管理员改余额甚至没有对应完整财务流水。操作审计是事后 best-effort，不能替代交易账本。
- 用户订单与兑换历史接口全量读取、前端分页；规模增长后应改服务端分页。

## 七、建议的修复路线

### 第一批：先使计量与扣款可信

1. 固定流量批次 + 原子去重；覆盖丢 ACK、超时、旧批次晚到、节点重启、旧入口排空。
2. 所有收费入口增量计量；保持多跳只算一次，明确额度的上报窗口误差。
3. 管理员余额并发保护，禁止普通表单保存覆盖新余额；购买新增幂等交易标识。
4. 修复不限额度哨兵、存量规则降级、SQLite 充值并发和过期时间规范化。
5. 自动续费绑定套餐/订阅身份；封禁取消扣费；暂停政策单独配置或清晰告知。

### 第二批：统一套餐业务，而不是继续堆开关

| 动作 | 推荐语义 |
|---|---|
| 充值 | 只增加余额，不隐式切换/续购套餐 |
| 流量包续购 | 增加剩余流量，不返还历史消耗 |
| 月付首次开通 | 当前时刻开一个 30 天周期，设置固定周期额度 |
| 月付提前续费 | 购买下一周期，当前周期额度不变；到周期边界重置 |
| 立即重置 | 单独明确收费动作，展示旧剩余失效与新周期时间 |
| 自动续费 | 与手动周期续费共用同一业务服务与交易账本 |
| 切换套餐 | 显示前后额度、有效期、可用线路、超额规则处理；未确认不扣钱 |
| 注册 | 明确免费试用/待开通，不把未付费目录选择冒充有效订阅 |
| 管理员赠送 | 独立的免扣余额开通/赠送动作，留原因；不要求“先改余额再代购” |

保留旧 time 套餐兼容已有用户，短期不要强制迁移。新售商品可以收敛为“流量包”和“30 天月付”，减少组合歧义。

增加订阅当前周期起止、下次重置点、已付未来周期或独立预购记录；保留历史用量，不把累计统计与当前权益计数混用。

### 第三批：补运营与支付闭环

- 余额账本：交易号、来源、增减金额、前后余额、关联订单/兑换/退款、操作者和原因，与余额原子提交。
- 购买订单：区分首次/续费/切换/重置/自动续费，保存成交权益快照和周期，不只存套餐名、价格。
- 财务动作与普通操作审计分开；前者不能 best-effort 丢失。
- 再决定接什么支付渠道，补回调验签、金额币种核对、幂等、状态机、退款和对账。
- UI 增加账户状态、剩余额度、下次重置时间、续费失败原因、变更重新授权提醒；先解释清楚，再减少说明文字。
